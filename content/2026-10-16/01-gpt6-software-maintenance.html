01 / TARGETS

미사용 코드와 오래된 실험은 확인 방법이 다르다

코드가 호출되지 않는지, 실험 설정이 더는 필요 없는지는 서로 다른 증거로 판단한다.

정리 대상놓치기 쉬운 경우확인할 근거
미사용 코드 reflection, 동적 참조, 장애 대응용 경로 때문에 정적 검색에서 호출을 찾지 못할 수 있다. 호출 위치와 래퍼·별칭, 런타임 프로파일, 관련 변경 이력과 테스트를 대조한다.
오래된 실험·feature flag 코드가 현재 실행 중이거나 eligibility가 바뀌면 다시 활성화될 수 있다. 이름이나 생성 시점만으로는 사용 종료를 판단할 수 없다. 현재 실험 플랫폼 설정, 간접 참조, 서비스 간 사용, 겹치는 PR, 평가 횟수와 CPU 비용을 확인한다.
느리거나 불안정한 CI 테스트를 줄이는 변경이 실제 회귀 위험을 높이거나, 한 번의 실행 시간만 보고 병목을 잘못 고를 수 있다. 최근 CI 기록에서 실행 시간과 flaky 패턴을 확인하고, 기존 테스트를 보존하는 수정부터 제안한다.

GPT-6 Astra는 넓은 dead-code 요청에서 과거 PR, 내부 대화와 프로젝트 기록, 프로파일 자료를 함께 조사했다. 오래된 실험을 조사할 때도 현재 설정과 코드 사용처를 대조했다. 이런 외부 자료를 볼 수 없다면 모델은 그 한계를 표시하고, 추정으로 사용 종료를 확정하지 않아야 한다.

↳

삭제 근거는 코드 안에만 있지 않다. 동적 참조, 현재 설정, 사용 빈도와 운영 목적을 함께 확인해야 안전한 정리 후보를 만들 수 있다.

02 / SAFEGUARDS

운영 제어는 보존하고, 증거는 표로 남긴다

오래되어 보이는 설정도 장애 대응이나 향후 차단을 위해 남겨 둔 제어일 수 있다.

  1. 간접 사용을 조사한다. enum, 상수, 래퍼, alias, schema, 동적으로 조립한 이름, 다른 서비스의 소비자를 확인한다.
  2. 운영 설정의 현재 상태를 확인한다. 실험 콘솔이나 설정 저장소를 읽고, git 기록이나 코드의 상수만으로 현재 상태를 추정하지 않는다.
  3. 의도된 안전 장치를 구분한다. kill switch, 비상 차단, 운영 보호 게이트의 목적을 확인한다. SDK fallback과 로컬 override도 조사 범위에서 어떻게 다룰지 명시한다.
  4. 효과를 측정한다. 실행 횟수와 프로파일이 있으면 CPU 사용량 등 제거 후보의 비용을 확인하고, 기대 효과와 불확실성을 함께 기록한다.
  5. 운영 변경을 제안으로 제한한다. 보고서와 작은 draft PR을 준비하고, 실제 설정·서비스 변경은 별도 검토 후 진행한다.

기사의 한 사례에서 Astra는 여러 기능 flag에 연결된 내부 override가 CPU fan-out을 일으킨 사실을 발견했다. 설정 콘솔에는 해당 flag가 “Permanent”로 표시되어 있었으므로 자동 삭제하지 않고 사람의 검토 대상으로 올렸다. 검토 뒤 제거했으며, 주 영향 서비스의 CPU를 약 0.42% 줄일 것으로 추정했다.

03 / MODEL COST

같은 조사에서 모델·추론 강도별 비용을 비교했다

비교는 같은 stale-experiment 조사 prompt를 사용하고, 저장소의 특정 하위 디렉터리에서 진행했다.

모델·강도API 비용발견 수발견 1건당 비용
GPT-6 Astra Ultra$109.06142$0.77
GPT-6.1 Sol Ultra$15.12131$0.12
GPT-6.1 Sol Medium$5.2786$0.06

이 실험에서 Sol Ultra는 Astra Ultra 발견 수의 92%를 찾았고 API 비용은 14%였다. Sol Medium은 발견 수가 더 적었지만, 발견 1건당 비용도 낮았다. 모델 간 차이를 검토하자 Astra가 찾고 Sol이 놓친 사례 중에는 다른 flag의 dependency로 쓰이는 상수가 있었다. 이 누락 유형을 prompt에 반영하면 더 낮은 비용의 설정도 개선할 수 있다.

비교 범위는 Python·TypeScript·Go·Rust로 된 6,000개 이상 파일, 약 100만 줄을 포함한 특정 저장소 하위 경로다. 비용은 표준 API 가격이며 조사 subagent와 자동 후속 작업을 포함한다. 발견 수는 병합된 수정 수가 아니며, 이 결과를 다른 저장소의 성능 보장으로 해석할 수 없다.

04 / CONTEXT

AGENTS.md의 지침도 같은 조건으로 비교한다

에이전트를 잘못 이끈 지침 하나를 골라, 해당 지침만 바꾼 replay로 품질과 작업 비용을 확인한다.

이 replay 방법은 블로그의 “Other ideas to try”에 소개된 제안이다. 기존 지침과 수정 지침의 효과를 같은 조건에서 비교해 업데이트가 도움이 됐는지 확인한다. 블로그는 이 제안의 적용 결과를 별도 실험 수치로 보고하지 않았다.

05 / RESULTS

성과는 발견량이 아니라 측정한 변화로 판단한다

OpenAI 팀이 보고한 결과에는 코드 규모, 이미지 크기, CI 시간과 CPU 변화가 포함된다.

1,400+병합된 유지보수 PR
800K+삭제된 코드 줄
5명여러 저장소를 검토한 엔지니어

CI 조사 prompt는 최근 실행 기록을 보고, 하루 기준으로 절약할 CI 분을 추정해 제안을 우선순위화했다. 이 방식은 추상적인 “CI를 빠르게 해줘”보다 비용이 드는 작업과 기대 효과를 먼저 비교하게 한다.

06 / WORKFLOW

한 후보에서 시작해 근거가 쌓이면 범위를 넓힌다

모델이 찾을 수 있는 개선 후보가 많을수록 우선순위와 검토 비용이 중요해진다.

  1. 01작은 범위 선택후보 하나와 확인 기준을 정한다.
  2. 02근거 교차 확인참조·설정·이력·지표를 읽는다.
  3. 03효과와 위험 기록미확인 정보는 그대로 표시한다.
  4. 04사람 검토 후 제안선택한 변경만 작게 만든다.
  5. 05검토 결과로 확장누락 유형과 prompt를 갱신한다.
