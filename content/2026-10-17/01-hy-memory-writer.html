기억을 잘 쓰는 모델

Tencent의 Hy-Memory-30B-A3B는 대화에서 남길 사실을 고르고, 새로운 정보에 맞춰 외부 기억을 갱신하는 전용 모델이다. 답변 모델 전체를 바꾸는 것이 아니라 메모리 시스템의 writer를 교체한다. [1]

02 / EXAMPLE

좋은 요약보다 정확한 상태 변경이 중요하다

아래는 설명용 가상 대화와 기대 기록이다. 실제 모델의 생성 결과가 아니다.

가상 입력 · 두 번의 대화

10월 1일: “Aurora API는 FastAPI로 만들고 DB는 MySQL을 쓰기로 했어.”

10월 10일: “Aurora DB는 PostgreSQL로 바꿨어. FastAPI는 그대로야. 고마워!”

기억 품질을 판단하는 예시
기록 방식나중에 생기는 문제 또는 이점
“사용자는 백엔드를 개발한다.”프로젝트명, 프레임워크, DB 변경을 모두 잃는다.
MySQL과 PostgreSQL을 나란히 저장어느 것이 현재 결정인지 알 수 없다.
현재 / 과거 / 유지 조건을 구분Aurora의 현재 DB는 PostgreSQL. 10월 10일 MySQL을 대체했다. FastAPI는 유지된다.
인사말은 제외“고마워”를 장기 선호나 프로젝트 사실로 만들지 않는다.

이 예시에서 검사할 질문은 “지금 DB는 무엇인가?”, “언제 무엇에서 바뀌었나?”, “FastAPI도 교체했나?”다. 매끄러운 한 줄 요약인지보다 이 질문들에 근거 있게 답할 정보가 남아 있는지를 확인한다.

03 / TRAIN

먼저 쓰는 법을 배우고, 기억의 쓸모로 보상한다

논문 §4–6과 Figure 1의 핵심. [2]

STAGE 1 · ON-POLICY DISTILLATION

자기가 쓴 기억 위에서 연습

학생이 실제 프레임워크에서 쓴 기록과 출력을 교사가 지도한다. 자기 이전 출력이 만든 상태에서 다음 쓰기를 배운다.

STAGE 2 · ATTRIBUTED MEMORY RL

나중에 답할 수 있는 기억에 보상

같은 초기 bank에서 8개 후보를 전개한다. 최대 5개 chunk를 묶어 처리한다. 답변·채점 모델은 고정하고 writer만 학습한다.

chunk 점수 = PRM + 2 × ORM − 0.3 × 저장량 페널티

PRM은 chunk의 사실을 정확히 회수하는지와 저장하면 안 되는 내용을 걸러냈는지를 본다. 여기서는 숨은 추론과정 채점이 아니다. ORM은 여러 chunk를 연결한 답변의 근거를 출처 chunk에 귀속한다. 페널티는 무조건 많이 저장하는 편법을 억제한다.

Chunk-level GRPO는 같은 chunk 위치의 후보끼리 점수를 비교한다. 다음 window에는 총점이 가장 높은 후보의 마지막 bank를 넘긴다. chunk별 최고 기록을 짜깁기하지 않는다.

학습된 프레임워크: Mem0, MemOS, Hy-Memory의 Chat·Working·Coding. EverMemOS는 학습에 넣지 않은 평가 환경이다. [2]

이 설계에서 아직 검증이 필요한 부분

보상별 통제 실험·반복 seed·사람과 judge의 일치도 검증이 남아 있다. 근거 귀속은 인과관계 증명도 아니므로, 개별 기법의 기여를 단정하지 않는다. [2]

05 / STACK

모델 · SDK · MemHub를 구별하자

비슷한 이름이지만 교체하거나 도입하는 단위가 서로 다르다.

구성요소의 책임
구성요소하는 일따로 필요한 것
Hy-Memory-30B-A3B기억 쓰기에 특화된 모델 가중치추론 엔진, 저장·검색 시스템
Hy Memory SDK추출·충돌 조정·저장·검색을 연결LLM endpoint와 embedding endpoint
MemHub사용자가 허용한 여러 AI 앱의 기록을 관리·재사용하는 제품수집·모델 처리·다른 앱의 읽기에 대한 각각의 권한

SDK의 lite는 raw 기록의 embedding 중심이며 writer LLM을 호출하지 않는다. pro부터 LLM 추출과 reconcile을 사용한다. ultra는 graph와 추가적인 기억 진화를 포함한다. 따라서 writer 모델을 비교할 때 lite만 시험하면 목적과 어긋난다. [4]

working은 작업 사실과 재사용 가능한 경험을, coding은 여기에 코드 변경 이력을 더한다. 현재 SDK에서 working/coding 쓰기는 tool trace가 필요하며, 없으면 chat으로 돌아간다. Coding 검색 시에는 scene, user_ids, workspace_id를 명시하고 branch도 일관되게 관리한다. branch 필터에는 branch가 없는 공통 기록이 포함될 수 있으므로 엄격한 보안 경계로 간주하지 않는다. [6]

MemHub의 local-first는 모든 모델 처리가 자동으로 오프라인이라는 뜻이 아니다. 연결한 endpoint와 권한을 별도로 확인한다. 모델 파일만 받아도 Codex·Cursor의 기억이 자동 공유되는 것은 아니다. [7]

06 / MEMORY

3B 활성 ≠ 3B 가중치만 올린다

활성 파라미터는 토큰별 계산 규모의 단서다. 상주 가중치, KV cache, 실행 버퍼는 별도로 계산한다.

공개 config.json에서 확인한 구성 [3]
아키텍처HYV3ForCausalLM / hy_v3
Transformer48 layers · hidden size 2,048
MoE128 experts · token당 8개 선택 · shared expert 1개 · 첫 MLP는 dense
Attention32 query heads / 4 KV heads · head dimension 128
설정상 위치 한도262,144 tokens. 해당 길이의 품질·속도 보증이나 장기 저장소 용량을 뜻하지 않는다.

[3] 모델 설정과 [9] 약 60.1 GB로 표시된 파일 저장소를 확인했다. 아래 값은 30B를 반올림해 계산한 가중치 payload 추정이며 실제 양자화 배포판의 크기가 아니다.

자체 산술 추정 · 가중치만 · 1 GB = 10⁹ bytes
정밀도 가정계산payload주의
BF1630B × 2 bytes약 60 GB / 55.9 GiB일부 FP32 tensor·런타임 버퍼 별도
8-bit30B × 1 byte약 30 GB / 27.9 GiBscale·고정밀 tensor 별도
4-bit30B × 0.5 byte약 15 GB / 14.0 GiB이 표는 해당 형식의 지원·품질을 보증하지 않음

공개 attention 설정에 일반적인 BF16 KV 저장을 가정하면, token당 2 × 48 × 4 × 128 × 2 = 98,304 bytes, 즉 96 KiB다. 단일 sequence의 실제 보유 KV 길이가 8,192 / 32,768 / 262,144 tokens이면 약 0.75 / 3 / 24 GiB가 된다. 이는 KV 분할·공유·양자화·padding을 반영하지 않은 논리적 payload 계산이다.

!

가중치가 들어가는 것과 긴 문맥·동시 요청까지 실용적으로 처리하는 것은 다르다. 처음에는 짧은 문맥과 동시 요청 1개로 시작해 peak VRAM과 쓰기 지연시간을 측정한다. GGUF·MLX·AWQ·SGLang 등은 이 글에서 동작을 검증하지 않았다.

07 / TRY

모델 호출과 영구 저장을 나눠 시험한다

실행 전 검토용 예제다. GPU에서 실행하거나 속도를 측정하지 않았다.

공식 카드가 명시한 테스트 버전은 vLLM 0.31.0이다. 아래의 8K 문맥·동시 요청 1개·localhost 바인딩은 초기 실험용 제안이며 공식 벤치마크 설정이 아니다. [1] [8]

# CUDA/PyTorch 호환성을 확인한 별도 환경에서 실행
pip install 'vllm==0.31.0'
vllm serve tencent/Hy-Memory-30B-A3B \
  --served-model-name hy-memory \
  --host 127.0.0.1 --port 8000 \
  --dtype bfloat16 --max-model-len 8192 --max-num-seqs 1
1단계: JSON 기억 후보를 추출하는 API 요청 
curl --fail-with-body --max-time 120 \
  http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "hy-memory",
    "messages": [
      {"role": "system", "content": "Extract only explicit durable user facts. Do not infer. Return a JSON object with a memories list of strings."},
      {"role": "user", "content": "나는 Python을 주로 쓰고, 설명에 코드 예제가 있는 것을 선호해."}
    ],
    "temperature": 0,
    "max_tokens": 512,
    "chat_template_kwargs": {"reasoning_effort": "no_think"}
  }'

HTTP 성공만 보지 말고 choices[0].message.content가 JSON으로 파싱되는지, memories가 문자열 배열인지, 입력에 없는 사실이 생기지 않았는지 확인한다. 이 요청 자체는 영구 저장을 수행하지 않는다.

2단계: Hy Memory SDK의 writer endpoint 연결

LLM과 embedding 설정은 서로 다르다. 기존 embedding endpoint·모델·실제 출력 차원을 먼저 설정해야 한다. 아래 가드는 필수값이 없으면 중단한다. [5]

pip install 'hy-memory==2.0.1'
export MEMORY_LLM_PROVIDER='openai'  # API 형식; 로컬 vLLM에 연결
export MEMORY_EMBEDDER_PROVIDER='openai'
export MEMORY_LLM_BASE_URL='http://127.0.0.1:8000/v1'
export MEMORY_LLM_MODEL='hy-memory'
export MEMORY_LLM_API_KEY='EMPTY'
export MEMORY_LLM_EXTRA_BODY='{"chat_template_kwargs":{"reasoning_effort":"no_think"}}'
export MEMORY_DATA_DIR='./.hy-memory-poc'

# 자신의 embedding 서비스 값으로 미리 export한 뒤 확인
: "${MEMORY_EMBEDDER_BASE_URL:?embedding endpoint 필요}"
: "${MEMORY_EMBEDDER_MODEL:?embedding 모델명 필요}"
: "${MEMORY_EMBEDDER_API_KEY:?embedding 인증값 필요}"
: "${MEMORY_EMBEDDING_DIMS:?실제 embedding 출력 차원 필요}"
export MEMORY_EMBEDDER_BASE_URL MEMORY_EMBEDDER_MODEL
export MEMORY_EMBEDDER_API_KEY MEMORY_EMBEDDING_DIMS
from uuid import uuid4
from hy_memory import HyMemoryClient

user_id = f"hym-poc-{uuid4().hex}"  # 반복 실행 시 기존 bank와 분리
client = HyMemoryClient(mode="pro")
try:
    client.add("나는 Python을 주로 쓴다.", user_id=user_id)
    result = client.search(
        "주로 사용하는 프로그래밍 언어는?",
        user_ids=[user_id],
        limit=5,
    )
    print(result)  # 검색 결과이며 최종 답변 모델의 응답은 아님
finally:
    client.close()

이는 chat 저장·검색 smoke test다. 기존 기억과의 충돌 해결, 재시작 후 복구, coding trace, 운영 권한까지 검증한 예제가 아니다. MEMORY_LLM_*는 SDK 공통 LLM 설정이므로 writer 외 LLM 사용 경로도 함께 바뀔 수 있다. 엄밀한 비교 실험에서는 검색·답변 측 모델과 설정을 따로 고정한다.

외부 embedding/API를 연결하면 기록이 해당 서비스로 전송될 수 있다. 먼저 가상 데이터로 시험하고, 실제 대화·키·bank 파일을 공개 저장소에 커밋하지 않는다. 외부 서비스의 비용과 데이터 정책도 별도 확인한다.

복구·삭제저장 후 재시작, 수정, 삭제, 재검색기록이 복구되고 삭제 정책이 검색·파생 데이터에도 반영되는가?

추천 순서: 가상 한국어 대화로 추출 → 빈 bank에서 두 writer 비교 → 재시작·삭제·격리 확인 → 실제 사용을 닮은 익명화 자료로 확장. 각 단계에서 실패한 사실과 원문 위치를 함께 남기면 단순 평균 점수보다 개선 방향을 찾기 쉽다.
